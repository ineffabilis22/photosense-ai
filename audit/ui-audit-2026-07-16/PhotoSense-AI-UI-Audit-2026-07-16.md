# PhotoSense AI 整体 UI / UX 审查

审查日期：2026-07-16  
审查对象：本地运行版本 `http://localhost:5173/`  
审查视口：桌面端 1440×1000；移动端 390×844  
覆盖页面：首页、开始点评、分析报告、历史记录  
数据状态：1 条真实历史记录，综合评分 74  

> 本报告是专家启发式审查，不等同于新一轮真实用户测试。登录、注册与分享属于当前阶段已明确暂缓的功能，因此不计入本轮视觉改造优先级。

## 1. 总体结论

PhotoSense AI 已经形成了有辨识度的“胶片暗房 / 老相机说明书”视觉方向。灰色颗粒底、暖白报告纸、焦橙强调色、编辑式网格和摄影图像之间有明确的概念联系，视觉语言不再像常见 AI 工具模板，这是当前版本最有作品集价值的部分。

但目前更像一套“风格明确的视觉概念稿”，还没有完全收敛成“高可读、可持续使用的产品界面”。主要问题并不是风格错误，而是视觉风格压过了信息可读性和操作效率：

1. 多处关键文字、按钮和说明的对比度不足，部分内容看起来像禁用态。
2. 移动端只是把桌面内容纵向堆叠，报告达到约 9290px，高频任务缺少针对窄屏的重新编排。
3. 桌面端又存在相反问题：历史记录、报告章节之间出现大量无意图空场。
4. 报告信息很多，但“总览、观察、诊断、后期、下次行动”的阅读层级还没有充分区分。
5. 视觉状态大多只通过颜色表达，键盘焦点、选择语义和页面标题结构存在明显无障碍风险。

## 2. 已经做得好的部分

### 2.1 品牌方向清楚

- 暖白纸张与灰色颗粒背景能自然联想到相纸、说明书和暗房工作台。
- 焦橙用于 CTA、评分和分类标签，具有显影液警示色与复古印刷色的感觉。
- 大幅摄影作品和编辑式排版，使产品不像通用 AI SaaS。
- 报告顶部“大结论 + 分数 + 雷达图”的组合有足够的视觉记忆点。

### 2.2 报告内容骨架合理

- 总览、照片、画面观察、五维诊断、后期建议、下次行动，基本覆盖了用户从“理解问题”到“采取行动”的需求。
- 桌面端侧栏目录能在长报告中提供位置感。
- “评分依据 / 结论 / 原因 / 行动”的重复结构，确实有利于快速扫读。

### 2.3 基础响应式与状态处理并非缺失

- 390px 下未发现整页横向溢出。
- 上传错误与分析状态已有 `alert/status` 语义。
- 页面包含 `<main>`，并已有全局 `:focus-visible` 与 reduced-motion 基础规则。
- 历史页有搜索、排序、介质、题材、日期和结果计数，功能骨架完整。

## 3. 最高优先级问题（P1）

P1 表示会明显阻碍主要阅读、操作或用户信任，应在下一轮视觉改造中优先完成。

### P1-01：关键文字与状态对比度不足

#### 证据

- 主题焦橙 `#d45a32` 对暖白 `#fff7ea` 约为 3.72:1，未达到普通文字建议的 4.5:1。
- 焦橙对纸色 `#e4dac3` 约为 2.85:1，甚至低于大号文字常用的 3:1 判断线。
- 页脚文字按当前 token 合成约为 2.37:1。
- 多组输入占位文字约为 2.23:1–2.72:1。
- 首页移动端主视觉把浅色正文直接叠在亮暗复杂的照片上，部分行几乎消失。
- 报告顶部四个操作按钮、图片说明、“裁剪参考”、步骤编号和页脚均呈现为近似禁用态。

#### 影响

- 用户无法区分“弱信息”和“不可操作”。
- 风格化纹理进一步削弱本来就不足的对比。
- 在亮度较低的显示器、户外或视觉能力下降的情况下，主要内容会不可读。

#### 建议

不要继续用“一个橙色 token 解决所有强调”。建立语义色角色：

- `accent-action`：用于按钮背景，颜色需足够深，允许暖白文字达到 4.5:1。
- `accent-text`：用于纸面小字，使用更深的砖红 / 暗橙。
- `accent-decorative`：可保留当前焦橙，但仅用于大面积色块、规则线与非必要装饰。
- `text-primary / secondary / muted / disabled`：分别定义，并禁止正文使用装饰色透明度临时凑灰度。
- 图片叠字必须使用稳定的暗色遮罩、实体色块或把正文移出照片；不能只依赖文字阴影。

#### 验收标准

- 普通正文和按钮文字对背景至少 4.5:1。
- 大号文字、图形边界和选中状态至少 3:1。
- 所有可点击控件不再仅靠颜色深浅区分状态。
- 在灰阶模式下仍能判断选中、禁用、当前和可点击状态。

### P1-02：移动端报告顶部结构失效

#### 证据

- 390px 视口下真实报告总高度约 9290px。
- 报告目录可视宽度约 317px，实际内容宽度约 712px，形成局部横向滚动。
- 首屏中 `01 / 02 / 03` 与标题发生拥挤和错位，滚动条本身成为显著视觉元素。
- 顶部四个操作按钮纵向堆叠，但文字和边框非常淡，既占空间又不形成明确操作层级。
- 用户在首屏仍看不到完整结论，需要继续滚动。

#### 影响

- 用户进入报告后首先面对的是低对比操作区和破碎目录，而不是分析结论。
- 横滑目录缺少明显提示，后方章节不易被发现。
- 长页带来位置迷失，尤其在返回修改或比较不同维度时。

#### 建议

- 移动端顶部只保留“返回”和一个主操作，其他动作进入更多菜单。
- 将五项目录改为可吸顶的横向 stepper，并显示清楚的“1/5”；或使用单行下拉目录。
- 目录标签使用短名称：“总览 / 诊断 / 后期 / 下次 / 设置”。
- 把结论和 74 分放入第一屏；雷达图可放在其后或折叠到“查看评分详情”。
- 对五维诊断使用可展开卡片，默认只展开最低分或最需改进的一项。

#### 验收标准

- 390px 首屏能看到报告结论与总分，不被工具栏和目录吞噬。
- 不出现无法解释的横向滚动条；若保留横滑，必须有完整首项、半露下一项和明确滑动提示。
- 用户从任意章节可在一次操作内回到目录或下一行动。
- 移动端报告总滚动长度在内容不丢失前提下减少约 25%–35%。

### P1-03：首页的“概念表现”压过核心价值表达

#### 证据

- 移动端首页总高度约 4428px。
- 主标题尺寸过大，正文叠在夜景照片上，浅色文字同时跨越天空、灯光和建筑，阅读稳定性很差。
- 维度数字和首页下半部分文字在灰色颗粒底上对比过低。
- 桌面端下半页的统计数字、说明文字和页脚同样接近背景。
- 抽象图形和长篇说明占用大量纵向空间，但不能比真实报告示例更快地解释产品价值。

#### 影响

- 用户能感受到“风格”，却需要较长时间才能理解“上传后到底获得什么”。
- 主要 CTA 下方的说明和能力维度被视觉弱化，降低继续探索的动力。

#### 建议

- 保留大图，但让标题位于实体纸片 / 暗色遮罩上；描述移至照片下方的高对比区域。
- 首屏结构收敛为：一句价值主张、简短说明、主 CTA、真实分析结果缩略图。
- 把五维能力从纯数字网格改为一行简要能力说明，移动端使用 2×3 网格而非松散堆叠。
- 降低大背景颗粒对正文区域的影响；颗粒用于画布，内容仍应放在干净表面上。
- 删除或压缩不能直接解释产品产出的抽象插图。

#### 验收标准

- 主视觉所有文字在任何照片区域都清晰可读。
- 用户在首屏可回答三个问题：这是什么、能得到什么、下一步做什么。
- 真实报告预览在移动端前两屏内出现。

### P1-04：移动端点评流程过长，上传与预览位置不符合任务顺序

#### 证据

- 点评页移动端总高度约 2426px。
- 顶部页头变成两行，占约 106px。
- 题材按钮退化为单列窄按钮，选项数量直接转化为长距离滚动。
- 用户要先经过大量设置才到上传和开始分析区域。
- 上传完成后的作品预览位于操作区之后，用户无法在上传后立即确认是否选对照片。

#### 影响

- 核心任务“上传照片”被配置项压到后面。
- 上传反馈不在操作附近，容易造成重复上传或怀疑是否成功。
- 单列按钮看起来像步骤，而不是一组选项。

#### 建议

- 移动端顺序改为：上传照片 → 预览与文件信息 → 三项配置 → 开始分析。
- 介质、口径、题材使用 2 列或 3 列选项；较少使用的解释放在展开说明中。
- 上传成功后自动滚动到预览，或把预览固定在上传卡片内部。
- 主 CTA 可在满足条件后吸附于底部，但不能遮挡正文。

#### 验收标准

- 上传入口在第一屏或紧邻第一屏。
- 上传成功后无需额外滚动即可看到缩略图、文件名与删除/更换入口。
- 所有配置按钮在 390px 下至少两列，除非标签长度确实不允许。

### P1-05：历史记录在少量数据时呈现“未完成”状态

#### 证据

- 桌面端只有一条记录时，卡片固定在最左侧，右侧约三分之二为空。
- 两层筛选和统计区占据大量首屏空间，真实内容只露出一部分。
- 卡片中的文件 ID 被硬拆成两行，视觉权重接近作品标题。
- 移动端筛选区远长于内容摘要，用户要滚动很久才能看到第一张卡。

#### 影响

- 在作品集演示的典型“一两条数据”场景中，页面显得缺内容、像网格没有加载完。
- 技术文件名抢走用户真正关心的“问题、分数、下一步”。

#### 建议

- 桌面端使用自适应网格。单条记录时做成 5–6 栏宽精选卡，并与摘要 / 最近进步组成两栏。
- 将高级筛选收起；默认只显示搜索、排序与“筛选”按钮。
- 卡片优先展示：作品名、日期、总分、最低维度、关键问题、下一次练习。
- 文件名截断中间并降为 metadata，完整值放在详情或 tooltip。
- 无记录或少量记录时加入明确的“开始第一次点评”或“继续积累复盘”的引导。

#### 验收标准

- 1、2、3、6 条记录下网格都保持视觉平衡。
- 移动端进入历史页一屏内能看到至少一张记录的标题或图片。
- 文件名不会强制换行破坏标题区。

### P1-06：报告入口与已有历史报告的关系不清楚

#### 证据

- 本轮实测中，历史记录已有一份报告，但从全局“分析报告”导航直接进入时仍显示“暂无分析报告”。
- 只有先进入历史并点击具体卡片，真实报告才会加载。

#### 影响

- 用户会误以为报告丢失或历史记录损坏。
- 全局导航“分析报告”的含义不明确：是当前报告、最新报告，还是空的临时状态。

#### 建议

- 明确定义为“最新报告”，直接打开最近一份；或改名“当前报告”，在无当前选择时展示历史报告列表。
- 空状态必须解释“报告保存在历史记录中”，并提供一键进入历史的主 CTA。

#### 验收标准

- 存在历史报告时，全局报告入口不会显示误导性的空状态。
- 用户最多一次点击即可从导航进入最新或最近查看的报告。

### P1-07：键盘焦点、选择语义和页面标题结构不可靠

#### 证据

- 部分标题输入、报告目录和登录输入显式清除了 outline，页面级规则没有可靠补回焦点。
- 隐藏文件输入仍留在 Tab 顺序中，可能形成 1×1 的不可见焦点停靠。
- 介质、口径、题材及历史筛选仅通过 `.active` 表达选择，没有 `aria-pressed`、`aria-checked` 或 radiogroup 语义。
- Review、Report、History 没有规范的页面级 `h1`；报告主要标题全部输出为 `h3`。
- 主导航没有 `aria-current="page"`；SPA 切页只更新 state 和滚动位置，没有把焦点移到新页面标题。
- 历史卡片用 `role="button"` 包裹，在管理模式下内部又出现原生按钮，构成嵌套交互控件。

#### 影响

- 键盘用户可能不知道当前焦点在哪里。
- 读屏用户无法确认当前选择、当前页面和报告结构。
- 管理历史时，内部操作的可访问名称与键盘行为可能不稳定。

#### 建议

- 为每个交互控件提供清晰、对比度足够的 `:focus-visible`，不得以 `outline: 0` 作为最终状态。
- 选择组使用原生 radio 或 `aria-pressed` 按钮，并提供组名。
- 每个页面一个 `h1`，报告章节使用 `h2`，维度和建议使用 `h3`。
- 切页后聚焦主标题或 `<main tabindex="-1">`；主导航增加 `aria-current`。
- 历史卡片使用明确的详情链接，选择与删除作为卡片外层同级操作。

#### 验收标准

- 只使用键盘可完成首页 → 点评 → 报告 → 历史的核心路径。
- 所有焦点可见，无不可见 Tab 停靠。
- 读屏可读出选项组名称、当前选择、页面标题和当前导航项。

## 4. 中优先级问题（P2）

### P2-01：报告长页节奏不稳定

- 有些章节之间出现约一至两个视区的大空白；另一些章节又连续堆叠高密度文字。
- “画面观察”标题在桌面窄列中被断成多行，标题区过高；移动端又与下方信息连续堆叠。
- 后期建议与下次行动前的空白过多，用户滚动时会同时看到上一章残片和下一章半页。

建议建立固定节奏 token：章节间 80–96px、标题到正文 24–32px、模块间 40–48px；移动端分别压缩到 48–64px、16–24px、24–32px。不要用内容高度或随意 margin 撑章节。

### P2-02：五维诊断缺少视觉优先级

- 五个维度大量使用近似字号、灰度和结构，阅读久了容易串列。
- 桌面采用第一排三项、第二排两项，右下出现一整列空槽。
- 每项都重复“评分依据 / 结论 / 原因 / 行动”，用户不容易快速定位最关键的一条。

建议突出最低分和“优先行动”，其余内容可折叠；桌面第二排两项各跨 1.5 列，或把空列改为“五维小结”。

### P2-03：报告总览中标题、摘要、评分三者比例失衡

- 大标题很有冲击力，但摘要字号和宽度偏小。
- 评分卡与标题卡像两个独立海报，缺少“结论对应此评分”的连接。
- 精确的 `74/100` 在评分口径说明之前出现，容易被理解成客观绝对质量分。

建议在评分旁标注“基于胶片摄影 / 进阶口径 / 静物摄影的学习参考”，并展示最低维度与一句评分依据；减小标题一档，把空间让给可操作摘要。

### P2-04：“补充说明”与“评价设置”仍不一致

- 目录写“05 补充说明”，正文标题写“评价设置”。
- 到达页面底部时，桌面目录仍可能高亮“04 下次行动”。
- 介质 / 口径 / 题材标签漂浮在正文右侧，与“本次评价基准”的关联不强。

建议统一名称为“评价依据”或“评价设置”，并在目录、锚点和正文中完全一致；标签移动到标题下方；接近页面底部时强制激活最后章节。

### P2-05：页面表面和纹理角色尚未制度化

- 暖白纸面上的正文通常可读，但灰色颗粒背景上的次级信息普遍偏弱。
- 一些内容浮在背景上，另一些进入纸面卡片，没有清楚的语义规则。
- 纹理在大背景、页脚和低对比文字同时存在时，会让画面显得浑浊。

建议定义三类表面：`canvas` 仅承载氛围；`paper` 承载主要阅读；`dark-panel` 承载照片和强对比操作。正文不得直接放在未经控制的 canvas 上。

### P2-06：移动页头占用空间且触控尺寸偏小

- 390px 下页头分两行，占约 106px。
- 移动导航字体约 0.68rem，登录 / 注册高度约 34px。
- 实测报告页“首页”导航文字目标宽约 22px，低于 WCAG 2.2 常用的 24px 最小目标判断；品牌按钮本体高度约 19px。

建议移动端使用单行品牌栏 + 菜单按钮，或保留一行可横滑主导航；主要触控目标统一至少 44×44px，文字至少 12–14px。

### P2-07：页脚和 metadata 过度弱化

- 页脚文字在灰色纹理上接近不可见。
- 报告图片说明、历史文件名和筛选结果计数都被处理为接近装饰的灰度。

建议把“非主要”与“不可读”区分开：metadata 仍应达到正文对比标准，可通过字号、位置和字重降低层级，而不是降低透明度。

### P2-08：动态反馈范围不够准确

- 整个报告 section 使用 `aria-live="polite"`，挂载长报告时可能形成过大的播报。
- 分享反馈、历史筛选计数不是明确的 status/live 区域。
- 报告自动保存到本地历史后缺少可见确认。

建议只让简短状态消息进入 live region；在报告顶部显示“已自动保存到此浏览器 · 查看历史”。

## 5. 低优先级润色（P3）

- 历史卡片 `NEW` 与橙色 CTA 争夺注意力；只在真正新建后的短时间显示。
- 抽象说明图形的造型统一，但信息含量低，可减少数量并换成真实裁剪对比、图上锚点或前后对照。
- 报告细线、编号框和小号橙色 kicker 过多，形成机械重复；每个区块最多保留一种装饰性强调。
- 过多全大写英文、等宽字和超小字会强化“说明书”风格，但中文界面不应牺牲阅读速度。
- 雷达图“技术完成度”标签在移动端有局部文本溢出，应缩写或允许合理换行。
- 上传文件名使用单行省略但没有查看完整内容的路径，可加入 title / 展开。
- JS 平滑滚动没有遵循 `prefers-reduced-motion`，需要在脚本中判断。
- 重复 sticky 页头没有“跳到主要内容”入口。

## 6. 分页面审查

### 6.1 首页｜健康度：中等偏弱

优点：首图有情绪，大标题有记忆点，主 CTA 明确，报告预览能建立产品专业感。

主要问题：

1. 移动端叠字不可读，是当前最直接的视觉缺陷。
2. 4428px 长度对于一个产品首页过长，且后半页内容价值递减。
3. 暗灰底上的正文、数字、页脚严重弱化。
4. 真实产品结果出现偏晚，抽象插图占比过高。
5. 桌面下半页长行正文和重复三列结构导致阅读疲劳。

### 6.2 开始点评｜健康度：桌面中等，移动端偏弱

优点：01–05 的配置顺序清楚，表单分组完整，禁用 CTA 能避免空提交。

主要问题：

1. 桌面左侧预览占据约 55% 宽度，但空状态只有一个小卡片，首屏空间效率很低。
2. 左侧说明和 metadata 对比不足。
3. 移动端题材单列导致页面过长。
4. 上传、CTA 和预览顺序不符合用户确认文件的心智模型。
5. 选中态依赖橙色，读屏无法获知当前值。
6. 禁用按钮和说明过淡，像页面加载失败。

### 6.3 分析报告｜健康度：桌面中等，移动端偏弱

优点：视觉身份最完整，结论与评分有冲击力，目录支持长文导航，报告内容有实际学习价值。

主要问题：

1. 桌面顶部操作区弱对比，并与报告主体脱节。
2. 大标题、摘要、评分比例失衡。
3. 图片说明和裁剪参考近乎不可见。
4. 章节间距与正文密度相互冲突。
5. 五维结构重复、第二排空列失衡。
6. 行动建议分散在多个章节，用户难以判断“现在先做什么”。
7. “补充说明 / 评价设置”命名和目录激活状态不一致。
8. 移动目录破碎、局部横滑、首屏无法聚焦结论。
9. 所有标题几乎都是 `h3`，不利于辅助技术和文档结构。

### 6.4 历史记录｜健康度：中等

优点：统计、搜索、排序、筛选和卡片已形成完整复盘框架；移动端卡片本身基本清楚。

主要问题：

1. 单记录桌面布局严重偏左。
2. 筛选控制比内容更抢占首屏。
3. 长文件名权重过高且硬换行。
4. 卡片没有展示关键问题、最低维度和下一次练习。
5. 管理模式下存在嵌套交互控件。
6. 少量数据和空数据状态缺少有意图的构图。

## 7. 核心流程健康度

1. **首页理解产品：中等偏弱。** 品牌感强，但价值信息被照片、纹理和长页稀释。
2. **配置并上传照片：桌面中等、移动端偏弱。** 控制完整，但移动端顺序和密度需要重排。
3. **阅读分析报告：桌面中等、移动端偏弱。** 内容有价值，导航、节奏、对比与行动层级影响吸收效率。
4. **回到历史复盘：中等。** 功能框架完整，但少量数据布局和卡片信息优先级不适合真实复盘。

## 8. 推荐的迭代顺序

### 第一阶段：可读性与状态基线

1. 重建语义色 token，并逐项修复对比度。
2. 修复首页照片叠字、报告按钮、图片说明、裁剪参考、步骤编号、页脚。
3. 补全焦点态、`aria-current`、选择组语义和每页 `h1`。

验证：自动对比测试 + 键盘走完整核心流程 + 390px / 1440px 截图复核。

### 第二阶段：移动端任务重排

1. 压缩移动页头。
2. 点评页改为上传优先，并把预览放回上传反馈路径。
3. 重做移动报告工具栏和目录；五维诊断采用渐进披露。

验证：390px 下上传、确认、分析、阅读最低维度、返回历史均不需要猜测横滑或反复回滚。

### 第三阶段：报告阅读体系

1. 统一章节命名和目录激活。
2. 建立固定间距节奏。
3. 强化“当前照片先改 / 本张后期 / 下次拍摄”三层行动。
4. 将图上锚点、裁剪预览或前后对照替换部分抽象图形。

验证：让首次使用者在 30 秒内指出照片最主要问题、最先修改动作和下一次拍摄练习。

### 第四阶段：历史与作品集完成度

1. 适配 0 / 1 / 2 / 多条记录。
2. 卡片改为复盘信息优先。
3. 收起高级筛选，补齐空状态 CTA。
4. 统一 footer、metadata、规则线和纹理强度。

验证：使用 0、1、3、12 条模拟数据分别截图审查。
