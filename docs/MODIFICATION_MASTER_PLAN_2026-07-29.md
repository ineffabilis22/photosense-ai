## 1. 已确认事实

1. 产品主闭环“选择点评语境 → 上传 → 分析 → 报告 → 历史复盘”已经成立，必须保护。
2. 当前视觉方向为 `Darkroom Constructivist v1`，照片、结论和主操作必须优先于纹理和装饰。
3. 当前自动化基线为 48 项测试通过，TypeScript 检查和生产构建通过。
4. 当前本地审计未配置真实 AI provider，因此真实输出质量、延迟、费用和稳定性尚未验证。
5. 当前分析图最长边约 768 px、JPEG 质量约 0.55，不足以支撑精细锐度、噪点、轻微失焦和纹理判断。
6. 移动端完整报告约 8,927 px 高，粘性目录存在覆盖标题和正文的问题。
7. 首页冷启动约传输 20 MB，其中两张纹理图约占 14 MB。
8. 登录、注册和用户入口是演示行为，不是真实账户系统。
9. 用户已明确不新增专门的双图 AI 比较功能；现有历史记录对比可以保留，但必须收紧可比条件。
10. 用户已明确全部修改完成前不部署远端。

## 2. 产品修改目标

### G1：让评分与评语具有可解释的参考价值

- 评分只能建立在足够清晰的输入、可见证据和明确版本上。
- 同图同设置的结果应具有可测量的稳定性。
- 只在同题材、同介质、同评分体系下计算成长变化。
- 高完成度照片允许没有明显问题；证据不足时允许不作确定判断。

### G2：让用户在 30 秒内理解报告

- 报告首个移动视口回答“照片怎样”和“最先做什么”。
- 保留完整五维诊断自然展示，不恢复会造成空白的收回机制。
- 建立摘要、证据、行动三层阅读路径。
- 评语尽量回到照片中的具体区域和关系。

### G3：让移动端主流程稳定、短而可操作

- 390 px 下不得出现目录遮挡、横向溢出或主操作难以到达。
- 上传后不需要滚动两千像素才能开始分析。
- 主要触控目标接近或达到 44 × 44 px。

### G4：让产品边界诚实且具备公开部署条件

- 示例报告、演示登录、历史保存范围和第三方图片处理必须清楚说明。
- 示例报告不得污染正式成长统计。
- 公开 API 必须有来源限制、限流、用量边界和安全的环境设置。

### G5：在视觉冻结后降低维护风险

- 先稳定行为和响应式，再拆分大型 `App.tsx` 与 CSS。
- 页面导航最终应支持真实 URL、浏览器前进后退和可分享深链接。
- 建立浏览器端到端、视觉回归和可访问性回归。

## 3. 优先级定义

| 级别 | 含义 | 处理原则 |
| --- | --- | --- |
| P0 | 可信度、数据正确性、明显布局错误或公开部署阻断项 | 必须在正式部署前完成 |
| P1 | 直接决定报告学习价值和目标用户体验 | P0 基础稳定后立即完成 |
| P2 | 性能、无障碍与界面精修 | 在核心行为稳定后完成 |
| P3 | 路由、拆分和工程治理 | 视觉与行为冻结后完成 |

P0 是“发布门槛”，不等于所有 P0 都必须在同一个代码批次完成。本项目暂不部署，因此执行顺序优先减少耦合和返工，同时保留全部 P0 作为最终发布阻断项。

## 4. 推荐实施顺序

### Batch 0：锁定基线与修改边界

优先级：P0  
风险：低  
目的：避免在已有未提交改动和多版本工作区中产生错误合并。

任务：

1. 记录实施前 `git status`、`npm run check`、`/api/health` 和当前测试数量。
2. 保存首页、点评、报告和历史页的 1440、760、390 px 基线截图。
3. 每个后续批次只修改与该批成功标准直接相关的文件。
4. 不在同一批次同时进行 UI 重排和大型组件/CSS 拆分。

验收门槛：

- 活动目录明确记录为 `deliverables/photosense-ai-github-current`。
- 已有用户改动没有被覆盖、还原或混入其他版本。
- 48 项测试基线、构建结果和视口截图可追溯。

### Batch 1：移动端正确性与产品诚实性

优先级：P0  
风险：低至中  
目的：先修复明显错误和会伤害信任的界面，不改变评分算法。

任务：

1. 修复移动端报告粘性目录覆盖标题和正文。
2. 让五个报告章节在 390 px 下完整可发现；可采用紧凑目录或有明确提示的横向导航。
3. 首页和照片墙内置结果明确显示“示例报告”。
4. 将 provider/API Key 等开发术语改为普通用户可理解的服务状态。
5. 登录和注册明确标记为演示；禁止空表单产生看似真实的登录成功。
6. 删除无动作的用户入口，或改成明确的演示说明入口；本批不实现真实账户。
7. 上传前说明图片发送对象、用途、浏览器历史保存位置和删除方式。
8. 示例报告不进入正式平均分和成长统计；优先方案是不自动写入正式历史。
9. 历史对比只在 `medium`、`genre`、`scoreVersion` 和后续分析版本一致时计算分差。

可能涉及：

- `src/App.tsx`
- `src/styles.css`
- `src/theme-darkroom.css`
- `src/utils/comparison.ts`
- `src/utils/history.ts`
- `tests/app-interactions.test.tsx`
- `tests/comparison-utils.test.ts`
- `tests/history-utils.test.ts`

验收门槛：

- 390 × 844 下滚动任意报告章节，目录不覆盖标题或正文。
- 键盘可到达全部目录项，焦点清楚。
- 首页、照片墙和报告中的示例来源不会被误认成实时 AI。
- 空登录表单不会进入已登录状态。
- 示例报告不改变正式历史平均分。
- 不可比记录只并列展示，不计算“提升/下降”。
- `npm run check` 全部通过；1440、760、390 px 无新增回归。

### Batch 2：分析输入与版本可追溯性

优先级：P0  
风险：中至高  
依赖：Batch 1 完成  
目的：先让模型看到足够证据，再讨论分数是否可信。

任务：

1. 分离“分析用图”和“历史缩略图”两条处理链。
2. 分析用图先以最长边约 1536–1600 px、JPEG 质量约 0.80–0.85 作为实验起点；不放大较小原图。
3. 历史缩略图继续使用较小尺寸，避免撑爆 `localStorage`。
4. 为请求体、像素尺寸和编码体积设置明确上限，并验证三种 provider 路径。
5. 历史报告新增可追溯元数据：`analysisVersion`、`scoreVersion`、`rubricVersion`、`promptVersion`、provider/model 标识和分析输入尺寸。
6. 旧记录继续可读；缺失新元数据时标记为 legacy，不伪造版本。
7. 稳定性不能只依赖进程内缓存；缓存键必须包含会改变判断的上下文和版本。

关键权衡：

- 提高分辨率会增加延迟、流量和模型费用，因此 1536–1600 px 是基准候选，不是未经测试就永久写死的结论。
- 不建议用持久缓存掩盖模型波动；缓存可减少重复费用，但标定必须测量真实重复结果。

可能涉及：

- `src/App.tsx`
- `src/utils/analysis.ts`
- `src/utils/history.ts`
- `src/types/report.ts`
- `server/analyze-photo.mjs`
- `server/config.mjs`
- `tests/analysis-utils.test.ts`
- `tests/history-utils.test.ts`
- `tests/server-provider-flow.test.ts`

验收门槛：

- 分析请求与历史缩略图使用不同尺寸策略。
- 1800 × 1200 测试图不会再被降到 768 × 512 后用于技术完成度判断。
- 超大图、透明 PNG、WebP 和小尺寸照片都有明确测试。
- 新报告可以追溯到模型、提示词、评分规则和分析版本。
- 旧记录仍能打开，但不会参与不可靠的跨版本分差。
- 记录分析体积、耗时和费用变化，确认收益大于成本。

### Batch 3：评分标定与人工基准

优先级：P0  
风险：高，但主要是研究风险而非代码风险  
依赖：Batch 2 完成并接入一个固定真实 provider  
目的：证明分数和评语是否真正具有区分度，而不是只验证 JSON 格式正确。

任务：

1. 建立 48–60 张内部参考集，覆盖现有六类题材、不同完成度、明显技术失败、优秀作品和有意偏离常规的作品。
2. 至少两位有摄影经验的评审者独立给出六档判断、主要证据和“是否存在明显问题”。
3. 每张照片在固定模型、固定设置下重复分析三次。
4. 统计同图稳定性、人工档位一致性、排序方向、强行找问题率、证据具体度和拒绝过度判断能力。
5. 对发现的系统性偏差只做局部调整：提示词、档位映射或维度定义一次只改一个。
6. 每次模型、提示词或规则变化都提升版本并重跑回归集。

方向性验收目标：

- 至少 80% 的同图三次结果完全同档。
- 至少 95% 的同图结果不超过相邻一档。
- 优秀参考照片的强行找问题率低于 10%。
- 高低质量照片的排序方向与人工判断基本一致。
- 80% 以上主要问题引用真实、可定位的照片证据。
- 低分辨率或证据不足时，不对锐度、噪点和焦点作过度确定判断。

本批明确不做：

- 不开发新的双图 AI 比较模型。
- 不用单一“人工平均分”替代证据和档位判断。
- 不为了让分数更分散而机械拉伸分数。

验收门槛：

- 有可复跑的参考集清单、人工基准、三次运行结果和偏差报告。
- 所有阈值均注明样本规模和限制，不对小样本作市场级结论。
- 只有通过本批后，才允许对外强调评分稳定性或比较价值。

### Batch 4：报告学习价值

优先级：P1  
风险：中至高  
依赖：Batch 2 的数据契约稳定；Batch 3 至少完成第一轮基准  
目的：让用户更快理解“为什么”和“下一步”。

任务：

1. 上传设置增加可选的“拍摄意图 / 最想获得的反馈”，保持三步主流程，不新增强制页面。
2. 将该意图纳入提示词和报告上下文，但不机械重复到每段评语。
3. 报告建立独立的“30 秒摘要”：综合判断、最关键证据、一项最优先行动和照片。
4. 移动端首个视口尽量进入综合结论或最优先行动；工具栏、警告和目录不得占满首屏。
5. 保留五项诊断自然展示，不恢复旧的展开/收回交互。
6. 为最关键判断设计真实照片证据：区域编号、可开关辅助线、局部放大或裁剪参考。
7. 明确说明百分制来自六档映射，是学习参考，不是权威排名。
8. 增加“有帮助 / 不符合拍摄意图”轻量反馈；第一阶段只保存在本地，不伪装成云端学习。
9. 上传后在移动端提供就近的“开始分析”主操作，减少长距离滚动。

可能涉及：

- `src/App.tsx`
- `src/types/report.ts`
- `src/utils/report.ts`
- `src/utils/analysis.ts`
- `server/analyze-photo.mjs`
- `src/styles.css`
- `src/theme-darkroom.css`
- 报告、分析和交互相关测试

验收门槛：

- 80% 以上内部测试者能在 30 秒内指出一项核心判断和一项行动。
- 每条最高优先建议符合“动作 + 区域/对象 + 程度或顺序 + 预期变化”。
- 390 px 报告不依赖折叠即可自然阅读。
- 用户意图为空时保持现有兼容行为。
- 视觉标注可关闭，不改变用户照片本身的像素和色彩。

### Batch 5：首页性能、移动端与无障碍

优先级：P0 发布门槛中的性能项 + P2  
风险：中  
依赖：Batch 1 和 Batch 4 的主要布局稳定  
目的：降低加载和操作成本，不改变品牌方向。

任务：

1. 将两张大型纹理资产转换为更合理的尺寸和格式，保持低强度材料感。
2. 首页只预加载首屏关键照片，其余照片懒加载；按视口提供合适尺寸。
3. 优先使用 AVIF/WebP，保留必要兼容回退。
4. 为眼睛按钮和照片墙交互增加短文字提示。
5. 辅助标签不低于稳定可读字号；关键正文默认不低于 15 px。
6. 将胶片缩略图和登录/注册等边缘触控目标提高到约 44 px。
7. 报告导出菜单支持 Esc 关闭、正确焦点进入与返回。
8. 统一用户可见日期格式。
9. 评估自托管字体或可靠系统回退，减少外部字体失败影响。
10. 完成真实手机、键盘、200% 缩放、读屏和减少动态效果检查。

量化目标：

- 1440 px 首页冷启动初始传输由约 20 MB 降至 5 MB 以内。
- 390 px 首页冷启动初始传输目标为 3 MB 以内。
- 首页、点评、报告和历史在 1440、760、390 px 均无横向溢出。
- 键盘可以完成上传、开始分析、章节跳转、导出和历史回看。
- 普通文字和关键控件达到 WCAG AA；所有例外有记录和理由。

验收门槛：

- 保存优化前后资源清单、传输体积和截图。
- 照片没有被滤镜、低清替代或错误裁切。
- `prefers-reduced-motion` 下无必要动画停止。
- `npm run check` 全部通过。

### Batch 6：公开服务安全与隐私门槛

优先级：P0  
风险：高  
依赖：准备公开部署时执行；可以与 Batch 3–5 独立设计，但必须在部署前验收  
目的：防止服务器 Key、费用和用户图片被无边界使用。

任务：

1. 将通配 CORS 改为明确来源白名单，并区分本地开发和生产配置。
2. 增加请求体大小、请求频率、并发数和单次超时限制。
3. 定义用量控制方案；单实例内存限流只可作为原型方案，正式公开服务应评估持久或边缘限流。
4. 确保 provider Key 只存在服务器环境变量，不进入前端构建、日志或健康接口。
5. 生产环境强制关闭无账号保护的服务器历史导出，并保留自动测试。
6. 生产日志不输出报告正文、图片数据 URL 或完整供应商响应。
7. 在界面和文档中说明图片处理方、用途、保存范围、删除方式和失败处理。
8. 部署验收加入费用上限、错误率和异常流量检查。

验收门槛：

- 非白名单来源不能调用分析接口。
- 超限请求返回清楚且不泄密的状态。
- 生产健康接口不暴露 Key、模型内部配置或用户数据。
- 历史导出在生产环境返回禁止状态。
- 有真实 provider 的一次完整部署前演练，但用户批准前不发布。

### Batch 7：视觉冻结后的工程治理

优先级：P3  
风险：高  
依赖：Batch 1–6 的界面和数据契约稳定  
目的：降低后续维护成本，不改变产品行为。

任务：

1. 引入真实 URL 路由、浏览器前进后退和可分享深链接。
2. 页面切换时清理旧报告 hash。
3. 按页面和报告区块拆分 `App.tsx`，保持状态模型和 DOM 语义。
4. 按页面拆分 CSS，统一重复覆盖和 700–900 px 间的断点策略。
5. 建立浏览器端到端、视觉回归、自动可访问性和报告导出测试。
6. 修正文档中的测试数量漂移。
7. 加入真实 provider 延迟、错误率、费用和模型漂移监控。

验收门槛：

- 拆分前后 48 项现有测试及新增测试全部通过。
- 1440、760、390 px 视觉基线无非预期变化。
- 浏览器返回、刷新和深链接行为有自动测试。
- 不在本批顺带重新设计页面。

## 6. 风险控制

### 低风险，可先做

- 移动目录遮挡。
- 示例来源标签。
- 演示登录说明和空表单限制。
- 普通用户服务状态文案。
- 对比条件收紧。
- 上传隐私说明。

### 中风险，需要数据迁移与兼容测试

- 分析图与缩略图分离。
- 新增分析版本元数据。
- 示例报告不进入正式统计。
- 拍摄意图进入报告上下文。
- 报告摘要信息层级重排。

### 高风险，禁止和大规模 UI 改动混在一起

- 评分规则或档位映射变化。
- 真实 provider 稳定性与费用策略。
- API 限流和来源控制。
